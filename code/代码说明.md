`Markdown 全文切块 -> Prompt A 多次抽取候选 -> 解析 Markdown 候选 -> 同 chunk 去重 -> 多轮聚类 -> Nemotron 归并 -> 三模型评分 -> 中位数聚合 -> 输出工件`

## 2. 论文怎么切分

当前切分逻辑在：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:92)

### 2.1 先按 Markdown 标题维护 section 路径

代码用这个正则识别标题：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:10)

规则是：

- 遇到 `#` 到 `######` 开头的行，就把它当作标题。
- 标题会进入一个 `heading_stack`。
- `heading_stack` 用来记录当前段落属于哪条标题路径。
- 例如：
  - `## Discussion`
  - `### Limitations`
  - 那么该段落的 `section_path` 就会变成 `["Discussion", "Limitations"]`

对应实现：

- 当前 section 路径生成： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:102)
- 遇到标题时更新标题栈： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:133)

### 2.2 再按“空行分段”切 paragraph

当前不是滑动窗口，也不是固定 token 长度切分。
当前是典型的 Markdown 段落切分：

- 连续非空行会先进入 `paragraph_buffer`
- 一旦遇到空行，就触发一次 `flush_paragraph()`
- 把这一整段当作一个 paragraph

对应实现：

- 段落缓存： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:98)
- 空行时触发 flush： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:147)
- flush 逻辑主体： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:105)

换句话说，当前的 chunk 基本单位是：

- “标题路径 + 一个 Markdown 段落”

### 2.3 过滤掉不进入抽取阶段的段落

段落不是全都保留，当前会先做一次噪声过滤，逻辑在：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:39)

当前会过滤掉这些内容：

- 空段
- 位于 `references / bibliography / citation` 这类 section 下的段落
- 字符长度小于 `chunk_min_chars` 的段落
- 很像参考文献条目、标点密度异常高且带年份的段落

其中：

- 参考文献 section 判断： [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:34)
- 最小长度阈值默认值在 [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:93)，当前是 `120`

### 2.4 超长段落会再按句子拆开

如果一个 paragraph 太长，不会直接整段送给模型，而是会继续切。

逻辑在：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:61)

规则是：

- 如果段落长度不超过 `chunk_target_max_chars`，直接保留
- 如果超过上限，先按句号/问号/感叹号切句
- 再把句子重新拼成多个小 chunk
- 如果句子切不开，就按字符长度硬切

当前句子切分正则：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:11)

当前最大长度默认值：

- [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:94)

现在的默认值是 `1800` 字符。

### 2.5 chunk 最终长什么样

每个 chunk 都会带这些字段：

- `paper_id`
- `chunk_id`
- `section_path`
- `chunk_index`
- `chunk_type`
- `priority`
- `char_count`
- `chunk_text`

结构定义在：

- [models.py](/c:/science/sciquery/code/sciquery_pipeline/models.py:8)

写入工件的位置在：

- [pipeline.py](/c:/science/sciquery/code/sciquery_pipeline/pipeline.py:37)
- 输出文件：`output/{paper_id}/01_chunks.jsonl`

### 2.6 当前的 priority 是怎么打的

priority 目前只是一层标签，不参与当前全文测试模式的裁剪。

规则在：

- [markdown_processing.py](/c:/science/sciquery/code/sciquery_pipeline/markdown_processing.py:14)

当前策略：

- section_path 里含 `summary / outlook / discussion / conclusion / abstract / limitation / future work` 判为 `high`
- 含 `results / methods / analysis` 判为 `medium`
- 其他判为 `low`

## 3. 切分示例

假设 Markdown 是这样：

```md
## Discussion

This review summarizes ...

Current models work well ...

## Conclusion

Future work should test ...
```

当前会得到大致这样的结果：

1. `chunk_0001`
   - `section_path = ["Discussion"]`
   - `chunk_text = "This review summarizes ..."`
2. `chunk_0002`
   - `section_path = ["Discussion"]`
   - `chunk_text = "Current models work well ..."`
3. `chunk_0003`
   - `section_path = ["Conclusion"]`
   - `chunk_text = "Future work should test ..."`

如果某一段超过 `1800` 字符，就会继续拆成多个 chunk，但 `section_path` 不变。

## 5. 去重、聚类、归并、评分分别是谁做的

### 5.1 同 chunk 去重

逻辑在：

- [dedupe.py](/c:/science/sciquery/code/sciquery_pipeline/dedupe.py:6)

当前只去掉这类重复：

- 同一个 `chunk_id`
- `normalized_topic` 一样
- `derivation_logic` 一样

也就是说，当前还不是全局语义去重，只是先去掉最明显的重复输出。

### 5.2 多轮聚类

逻辑在：

- [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:115)

当前做法是：

- 用 `topic + derivation_logic` 作为聚类文本
- 本地计算简化版 `TF-IDF + cosine`
- 相似度超过阈值就合到一起

相关实现：

- 分词： [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:20)
- 向量化： [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:46)
- 余弦相似度： [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:57)
- batch 内聚类： [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:66)
- 多轮聚类主入口： [clustering.py](/c:/science/sciquery/code/sciquery_pipeline/clustering.py:115)

当前阈值和批大小配置：

- 相似度阈值： [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:95)
- batch 大小： [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:96)

### 5.3 Nemotron 归并

Prompt 构造在：

- [prompting.py](/c:/science/sciquery/code/sciquery_pipeline/prompting.py:51)

真正调用和分轮归并在：

- [pipeline.py](/c:/science/sciquery/code/sciquery_pipeline/pipeline.py:182)

这里现在是：

- 先把 cluster 变成 merge item
- 按 `merge_group_size` 分组
- 每组调用一次 Nemotron
- 如果一轮之后结果仍然很多，再把 partial merged topics 继续送下一轮归并

当前 `merge_group_size` 配置在：

- [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:97)

### 5.4 三模型评分

评分 prompt 构造在：

- [prompting.py](/c:/science/sciquery/code/sciquery_pipeline/prompting.py:113)

三评审模型配置在：

- [config.py](/c:/science/sciquery/code/sciquery_pipeline/config.py:110)

执行评分在：

- [pipeline.py](/c:/science/sciquery/code/sciquery_pipeline/pipeline.py:227)

### 5.5 分数聚合与否决

逻辑在：

- [response_parsers.py](/c:/science/sciquery/code/sciquery_pipeline/response_parsers.py:90)

当前聚合方式：

- 各维度取三个 judge 的中位数
- `overall` 也取中位数
- 同时记录 `overall_spread` 和 `evidence_spread`
- 如果至少两个模型把 `evidence_alignment` 或 `feasibility` 打到 `< 3.0`，直接否决

## 8. 当前实现的几个局限

当前代码已经能跑，但要明确几件事：

1. 当前 chunk 切分仍然是“标题 + 段落”级别，不是更细的语义切块。
2. 参考文献过滤是启发式规则，不是严格解析。
3. 当前聚类是本地简化版 `TF-IDF + cosine`，还不是 embedding 聚类。
4. Nemotron 归并和三模型评分 prompt 已经收紧，但仍然要用真实论文做 live 测试来校正。
5. `mock` 模式只能测流程，不能代表真实模型效果。

### 10.4 什么时候会自动重跑

如果下列内容变化，对应阶段会自动失效并重跑：

- 输入论文路径变化
- `Prompt A` 模板内容变化
- `candidate_runs` 或候选温度变化
- 聚类阈值或聚类 batch size 变化
- `merge_group_size` 变化
- 上游阶段输出内容变化

## 10.6 候选阶段心跳文件

- `stage_progress.completed_calls`
- `stage_progress.total_calls`

如果只是外部中断进程，没有来得及走到最终收尾，也可以直接看 `run_heartbeat.json` 判断已经跑到哪一个 chunk。

## 10.8 超时与失败续跑

当前版本对两个最耗时阶段增加了“失败落盘后继续执行”：

- `02_candidates_raw.jsonl`：只记录成功的 DeepSeek 候选生成调用
- `02_candidates_failed.jsonl`：记录失败的 `(chunk_id, run_index)`、错误类型、错误信息和时间
- `07_topic_scores.jsonl`：只记录成功的 judge 评分
- `07_topic_scores_failed.jsonl`：记录失败的 `(topic_id, judge_model)`、错误类型、错误信息和时间

运行行为：

- 单次 `ReadTimeout` 不再直接终止整条流水线
- 失败调用会写入对应的 `*_failed.jsonl`
- 当前运行会继续处理后续 chunk 或 topic
- 下次重跑时，只会把成功调用当作已完成，失败项会再次尝试

额外说明：

- `Nemotron` 归并阶段仍然保持失败即中断
- 最终聚合阶段只接受三位 judge 全部成功的 topic；评分不完整的 topic 会等待后续补齐

## 10.9 切块参数调整

当前版本把切块相关参数拆成了四个概念：

- `noise_min_chars`
  - 低于这个长度的段落直接视为噪声
- `chunk_min_chars`
  - 不是噪声但太短的 chunk，会尝试和相邻同 section 的 chunk 合并
- `chunk_target_max_chars`
  - 理想 chunk 长度，超过后优先按强句边界拆分
- `chunk_hard_max_chars`
  - 绝对上限；强句边界拆不开时，会先尝试软边界，再退化到近似硬切

当前默认值：

- `noise_min_chars = 40`
- `chunk_min_chars = 180`
- `chunk_target_max_chars = 1000`
- `chunk_hard_max_chars = 1300`

句子切分也做了收紧：

- 强边界只认 `. ! ?`
- `Fig. / Ref. / Eq. / Sec.` 这类缩写不再被误判成句末
- `; : , which / where / while / that / and / but / or` 只作为超长文本的软边界候选，不作为默认句边界
## 10.10 Candidate Parser And Merge Fixes

- `02_candidates_raw.jsonl` now stores only candidate calls that were parsed successfully.
- `02_candidates_parse_failed.jsonl` stores parse-empty and parser-exception cases, and these calls will be retried on the next run.
- Batched clustering now runs one extra global consolidation pass after a no-reduction round, so cross-batch near-duplicates are not left unmerged forever.
- `parse_merged_topics()` no longer pads `implementation_steps` to three items. Invalid step counts are preserved for downstream judge vetoes.
- Later merge rounds now carry forward `source_chunk_contexts` instead of collapsing to `" ".join(evidence_quotes)`, so source evidence does not get progressively thinner.

## 10.11 Merge Group Resume

- `05_merge_rounds` now supports per-group resume instead of only stage-level reruns.
- New merge-group files store `round_index`, `group_index`, and `group_signature`; reruns reuse any group whose signature still matches the current inputs.
- `05_merge_rounds/_resume_meta.json` stores the partial-resume stage signature for the current merge configuration.
- Older legacy `round_xx_group_xx.json` files without `group_signature` are still reused in a compatibility mode when `paper_id` and `input_group_size` match, so interrupted runs created before this change can continue.
- The default Nemotron load was reduced by lowering `max_tokens` and removing the heavy thinking payload, which should reduce merge-stage timeouts.
